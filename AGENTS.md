# AGENTS.md

Guidance for AI agents and contributors working in this repository.

## Project

Personal portfolio site for a Principal Design Manager at Microsoft, showcasing a wide range of expertise. See [documentation/seed-spec.md](./documentation/seed-spec.md). It's becoming Atiya, a personal site anyone can have: public, private and shared pages on GitHub Pages, made and published with a desktop app, read with Classic (the default navigation) or a way to explore that plugs in, each opening sections through its section triggers. The whole plan, and where each part is specified: [documentation/atiya.md](./documentation/atiya.md).

### 3D "Little Planet" navigation POC

Spec, plan and Definition of Done: [documentation/poc-3d-navigation/](./documentation/poc-3d-navigation/spec.md). Conventions for agents working on it:

- **Pinned stack (exact versions only):** astro 7.3.3, @astrojs/react 6.0.6, react/react-dom **19.2.8** (R3F 9.7.0 requires `<19.3`), three 0.186.0, @react-three/fiber **9.7.0** (never the proxy's v10 canary), @react-three/drei 10.7.8, @react-three/postprocessing 3.1.1 + postprocessing 6.39.5 (needs three `<0.187`), zustand 5.0.15. See spec §5.1 for the full list.
- Use **R3F v9 / drei v10 APIs** (not v8 patterns, not v10 alphas). Use `WebGLRenderer` only: no WebGPU/TSL, no physics engine. The tilt-shift must always be on, on both tiers; bloom and vignette are `high`-only, and adaptive quality may drop them but never the tilt-shift.
- Movement model: **rotate the planet under a fixed player and camera** (spec §5.2). Keep simulation logic in pure, unit-tested TS modules under `src/game/math` and `src/game/systems`.
- All actionable UI (prompts, dialogs, menus) is **semantic DOM**, not in-canvas. The classic site must stay reachable from every state.
- `/play` uses a **capability-gated dynamic import**, not a `client:only` island. `src/game/platform/gate.ts` must never import React or three. Game code is emitted as `game-*` chunks, and gated-out devices must never request them.
- `window.__game` exists only in dev and `--mode test` builds, never in production.
- **The residents are the owner's** (desktop plan M3a): Chopper, the family, Prabin, his music and anything that names them are gated by `RESIDENTS` (`src/game/platform/residents.ts`, the build constant `__GAME_RESIDENTS__`: on for this repository, off for a site made by Atiya Studio). Gate a new resident `import()` with it and list its chunk in `RESIDENT_CHUNKS` and its files in `RESIDENT_ASSETS` (`integrations/site-only.mjs`); `build-starter.mjs` fails a managed build that still has one. On such a site the welcome is the site's person's (`platform/siteWelcome.ts`).

### Site design system (the website, not the game)

The landing, the classic site and the design library have their **own** design system, separate from the game's. Rules: [documentation/site-ui/design-system.md](./documentation/site-ui/design-system.md); look: [visual-language.md](./documentation/site-ui/visual-language.md). Read them before any change to the site's UI.

- **Four tiers, each made only from the tiers below it:**
  - tokens and foundations (`src/site/design/`, `src/site/scripts/`, `src/site/styles/`, `src/site/assets/`);
  - fundamentals (`src/site/components/fundamentals/`, tier 0 only);
  - compounds (`src/site/components/compounds/`, fundamentals and tier 0, never another compound);
  - layouts (`src/site/layouts/`, compounds and fundamentals).

  Pages (`src/pages/index.astro`, `src/pages/classic/`) use a layout and carry no `<style>`. The game and the site never import each other; the one shared helper is `withBase` (re-exported by `src/site/design/meta.ts`).
- **Tokens are W3C DTCG 2025.10:**
  - `site.resolver.json` merges the base set `tokens.json` with the theme contexts `tokens.light.json` and `tokens.dark.json`, then the contrast modifier (`tokens.contrast-more.json`, written inside `@media (prefers-contrast: more)`);
  - values are 2025.10 objects;
  - after a change, run `node scripts/build-site-tokens.mjs` (never hand-edit `src/site/styles/tokens.css`, `documentation/site-ui/tokens.md` or `src/site/design/responsive.ts`). It also writes the token changelog (`documentation/site-ui/token-changelog.md`, from `token-history.json`); `--check` fails until you run it.
  - **never rename or remove a token or prop in one step:** add the new one, mark the old one deprecated (a token's `$deprecated: "Use --new"`; a prop's JSDoc `@deprecated use x`), move every reader in the same change, and remove it after one release. `tests/unit/tokenChangelog.test.ts` and `deprecation.test.ts` fail on any use of a deprecated name.
  - every `c.*` group names who reads it in `$extensions["site.owner"]`: one component (only it may read the group) or `shared` (a family's common decisions: control, check, list, image, quote, icon, scrollbar, editor). A value every page needs is semantic (`--size-chrome-block`, the top bar's height), never another component's token (tested).
  - a `matchMedia` query or a picture's `sizes` never holds a rem literal: use `media()` and `sizes()` from the generated `src/site/design/responsive.ts` (tested). Press, pop, lift and zoom are `--scale-*` tokens; underlines `--underline-*`; the only `em` written in a stylesheet is `1em`.
- **Colour roles are `light-dark()` pairs.** The page follows the system unless `<html data-theme>` is set (the header's theme switch, `localStorage['site.theme']`). Never branch on the theme: a subtree switches with `color-scheme`. The one exception is a picture's dark mode version: `Image` takes `dark` and draws a `<picture>` with a `source[data-dark]`, which `followThemeInPictures` and PageShell's head script point at the theme; pass a picture's `dark` on wherever you draw it (the lightbox links carry `data-full-dark` / `data-thumb-dark`).
- **Components read tokens only:** never a primitive, never a raw value. Width media queries use only the breakpoint tokens (40, 56, 72 rem).
- **Recipes are written once** (fewer than 25 copied declaration blocks, tested): a type style is a `type.*` token (`font: var(--type-label)`); the picture's drop shadow `var(--c-image-shadow-filter)`; the disabled state, a wrapper's focus ring, a card that's one link, a field's parts, a check's layout, a combobox's suggestions, a disclosure's chevron and a row of tags are `base.css` recipes keyed by `data-press`, `data-focus-ring`, `data-card`/`data-card-link`, `data-field-part`, `data-check-part`, `data-suggestions`, `data-chevron`, `data-tag-list`; a picture's file is `PictureSource` (`design/pictures.ts`). A component is at most 500 lines (350 without its styles).
- **Compounds placed in a column are containers** (Collection, StoryCard, Carousel): `@container` at a size token the component owns (`c.<name>.query-*`, marked `site.container`), never a screen query or a literal; their scripts ask their own width (`narrowerThan`).
- **Fundamentals are sealed:** no `class` or `style` props. Compounds lay them out from their own wrappers and never restyle them. `:global` is allowed only in Prose, Lightbox and VideoEmbed (markup they didn't write).
- **Page-wide pieces are placed by the layout.** The Lightbox is one per page: a gallery or figure marks its links `a[data-lightbox="group"]` and never imports it.
- **Scrollbars are overlays** (design system §3): no native bar, no gutter, no arrow buttons; `scripts/scrollbars.ts` floats a frosted, indigo-tinted handle over the edge in use. A new scroller carries `data-scrollbar` (never `scrollbar-width: thin`, `scrollbar-color` or `::-webkit-scrollbar-thumb`: a unit test fails on them). The game keeps its own `.scroll-thin`.
- **Scripts run on every page:** the design library changes pages without a reload (Astro's `ClientRouter`, `PageShell`'s `router`, set only by the LibraryLayout, with the side nav kept by `transition:persist`). A component's client script sets up its elements through `each(selector, (el, signal) => …)` from `src/site/scripts/page.ts` (never a bare `querySelectorAll` loop) and passes `signal` to every `window`/`document`/media-query listener. A unit test holds this.
- **Every component documents itself:**
  - a doc comment (a summary, `@tier`, `@a11y`, `@key`);
  - a JSDoc comment on every prop;
  - a story in `src/site/stories/<Name>.stories.astro`, made of `<Example title>` blocks.

  The design library (`/design/`) builds its pages from these (`src/site/library/registry.ts`); nothing in it is kept by hand.
- **Icons** are Font Awesome Pro *Duotone*, imported one at a time from the owner's local library (`node scripts/import-site-icons.mjs <name>=<font-awesome-name>`: it updates `src/site/design/icon-set.json` and writes the generated `iconData.ts`; never hand-edit it, import only what's used, and look at each new icon: some library names draw something else). Components draw them with `svgOf` in two layers: the text colour over a spot-indigo secondary (`--c-icon-secondary`); a status or an icon on an accent fill is tonal (`data-icon-tone="tonal"`). The site's own icons (the planet) are SVGs in `assets-src/site-icons/`, listed as `file:<path>`. The game keeps Font Awesome Free. **Fonts** are the three self-hosted Google Fonts (Fraunces, Newsreader, Figtree), cut to the axes and weights the site uses by `python scripts/build-site-fonts.py` (it reads the pins from the `axes` tokens and writes `src/site/assets/fonts/` and `src/site/styles/fonts.css`; never hand-edit either; `--check` fails if stale). Only the library's type playground loads the full Fraunces. Never a font or icon CDN.
- **Phones** ([mobile-audit.md](./documentation/site-ui/mobile-audit.md)):
  - every `:hover` rule goes inside `@media (hover: hover)` and has an `:active` twin for touch (tested);
  - no sideways scroll from 320 px;
  - 44 px targets;
  - the header's action must stay reachable in the menu;
  - height queries use the `short` breakpoint token.

  Check with the E2E group "site on a phone".
- **Themes** (spec: [documentation/site-ui/theming.md](./documentation/site-ui/theming.md)): a site's look is a theme (spacing, corners, fonts, the type ramp, colours), and a theme only changes token values: `src/site/theme/` resolves it against the tokens (`base.ts`) and writes custom properties over `tokens.css`; never theme a component directly. Presets are code (`PRESETS`, read only); a person's own themes are `content/themes/`, imported fonts `content/fonts/` (self-hosted: never load a font from a third party at run time), the active one `content/site.json`'s `theme` (none: Atiya, which writes nothing). Generated colours are held to AA by `palette.ts` `RULES` (the same pairs this test holds the site's own palette to: change both together). The themes panel (`/_edit/theme/`, `ThemePanel.astro`, `scripts/themePanel.ts`) previews a draft through `localStorage['atiya.themeDraft']`, applied before first paint by the dev-only head script (`theme/draft.ts`); in Atiya Studio it docks beside the site (`apps/desktop/src/core/dock.mjs`). Check with `tests/unit/theme*.test.ts`, the editor E2E "editor: theme" and the app E2E "desktop: themes panel".
- **Enforced by** `tests/unit/siteDesignSystem.test.ts` (tokens, raw values, tiers, sealing, docs and stories, contrast in both modes, copy, base paths) and the E2E group "site design system" (`tests/e2e/site.spec.ts`).
- **Screenshots** (the `visual` Playwright project: `tests/e2e/visual*.spec.ts`): every story's examples and the key pages in light and dark at 360, 768 and 1280, edit mode's parts library and the game's gallery, compared with baselines in `tests/e2e/__screenshots__/` (made and checked on Windows). A visual change runs `npm run visual` (about 10 minutes) and, if it's meant, `npm run visual:update`, which lists what changed: look at each image before committing it. Never pass `--update-snapshots` by hand.
- **The scoreboard:** `node scripts/design-system-audit.mjs` re-takes the measures of the [design systems review](./documentation/site-ui/design-system-review.md) for the website, edit mode and the game; `--check` fails if one slips below its target.

### Game UI design system

The rules are in [documentation/game-ui/design-system.md](./documentation/game-ui/design-system.md). Read it before any UI change.

- **Tokens only.** Every colour, space, size, radius, shadow, duration, easing and layer comes from `src/design/tokens.json`, a DTCG 2025.10 file (colour objects, `{value, unit}`, shadow objects; never a string value) with three tiers:
  - `p.*` primitives, which are private: never use `--p-*` in component CSS;
  - semantic roles and scales;
  - `c.*` component tokens.
- **Sizes are rem,** so "Larger text" scales everything; px only for lines and outlines (`border.*`), blurs, the pill and the scrollbar. Every `@media` query writes a `breakpoint.*` value. A CSS parser (`postcss`) holds every declaration in every game stylesheet to tokens, with a named allow-list.
- **Styles beside their components, in layers.** A component's styles are its own stylesheet in `src/game/ui/styles/<name>.css`, imported by the module that writes its classes (Astro hoists it into the page: no JS, there from first paint). `src/styles/` holds only `global.css` (the layer order and imports), `base.css` (element and global rules) and generated files. Every stylesheet opens with `@layer tokens, base, primitives, components, cursors;` and keeps everything in its layer; never a shared game stylesheet or an unlayered rule (tested).
- **Owners, hover, contrast, direction:** every `c.*` group names its reader in `$extensions["game.owner"]` (a component, a class family or `shared`); only its owner reads it. Every `:hover` sits inside `@media (hover: hover)` with an `:active` twin. Every control class has a rule in its stylesheet's `@media (forced-colors: active)` block (system colours only there); `prefers-contrast: more` switches muted text, borders and lines to their `-strong` roles. Logical properties only (`inset-*`, `*-block-*`, `*-inline-*`, `text-align: start`). Every export in the UI files and every prop of the primitives and containers has a `/** … */` comment (tested).
- **The gallery** (`/play/gallery/`, `src/game/gallery/`) exists only in dev and `--mode test` builds (`size-report.mjs --prod` fails if it ships); a new exported game UI component gets an entry there (tested), and its screenshots are `tests/e2e/visual-game.spec.ts`.
- After any change to `tokens.json`, run `node scripts/build-tokens.mjs` (it also writes `documentation/game-ui/token-changelog.md`; the deprecation rule above applies). Never hand-edit `src/styles/tokens.css` or `documentation/game-ui/tokens.md`. `tests/unit/designSystem.test.ts` fails on:
  - raw values;
  - a token nothing reads;
  - stale output;
  - contrast below WCAG on either surface;
  - copy-rule breaks.
- **Header and view chrome:** Sound, Fast travel, View whole planet and Menu are icon-only buttons (named by `aria-label`); by the compass there's only Reset. Full planet (P, or its button; docs: `documentation/poc-3d-navigation/full-planet.md`) is its own module in the nature chunk (`camera/overview.ts`, pure rules in `overviewMath.ts`): it turns the `world` group (never the camera's yaw), widens the tilt-shift's focus (never turns it off) and leaves the world exactly still when it's off; the fog's range follows any camera pulled back (`fogScale` in `world/timeOfDay.ts`), so a fast travel's fly-over keeps the planet clear. Fast travel (T, or its button) is the menu dialog's travel page: a tile per place with its sign, and a number key each (the plaza is H); it's also the parallel DOM route to every landmark (spec §6), so there's no hidden Tab-revealed list. The backpack opens and closes with I or B. A shortcut pressed with the focus on nothing (the page's body) goes to the planet (`onStrayKey`), so the keys always work; never take keys from a focused control. Turning and tilting without a drag (WCAG 2.5.7) live in the menu's View group; don't add buttons back round the compass. Scrolling surfaces use the thin scrollbar (`.scroll-thin`, `--c-scrollbar`).
- **Keys: E does, Space goes back** (design system §6.7). Space (the `back` action) stands up, gets off the swing, ends a conversation, stops an action and closes dialogs and panels (`spaceBack(e)` in `input/keyboard.ts`, which leaves Space to a focused text field, checkbox, radio or slider; on a backpack slot it's the right-click). Esc keeps working, but prompts, buttons and copy show Space, never Esc. With nothing to go back from, Space jumps (`PlanetSim.jump`; `controller.jump`): going back always wins.
- **Game panels hold a fixed size** (nothing grows or jumps as you pick) and never spell out their controls inline: the keys go in the head's help popover (`HelpPopover` in `ui/InventoryPanel.tsx`, the `help` prop).
- **Cursors** (design system §4): the game (`body.play`) uses its own, generated by `node scripts/build-cursors.mjs` from Font Awesome Free shapes into `src/assets/cursors/` and `src/styles/cursors.css` (never hand-edit either; the script holds each state's selectors and finds the hotspots). A new clickable thing in the game gets the pointer there. Over the ground the region carries `data-cursor="walk"`, and a landmark under the mouse `data-hover="landmark"`: set cursors through those, never `document.body.style.cursor`.
- **Click to walk** leaves a marker where the character is going (`WalkMarker` in `world/cues.tsx`, from `controller.walkMark`): a ripple, then a ring until the walk ends.
- **Surfaces:** components read colour only through `--surface-*` roles.
  - The game is **wood**: `body.play` and its panels carry `.surface-wood`; primary actions are gold.
  - **Paper** is the default surface on `:root`. The website's pages (landing, classic) have their own system since 2026-09-29 (see **Site design system** above) and no longer use it.
  - A new surface must define every role and re-declare `color`.
- **Reading on the planet** (documentation/sections/spec.md §6; design system §6.8): a building opens its list and pages as the site's own pages (`/play/<building>/…`, `src/site/content/PlanetPage.astro`, the layouts' `frame`), framed over the planet by the reading overlay (`ui/Dialogs.tsx`). The frame's script (`src/site/scripts/planetFrame.ts`, link rules in the pure `frameLinks.ts`) keeps every move inside the building (the site's router swaps the page in place, replacing its history entry, so there's no blank frame between pages; `location.replace` only as a fallback), and a link to another building gets a note, not a visit. The overlay shows the frame only once its page says it's ready (`data-ready`, faded in). The game and the frame talk by `postMessage` on the same origin; never import the site from the game to do it.
- **One thing asks at a time.** The bottom-centre focus lane and the bottom-left aside are decided by the pure `src/game/ui/lanes.ts` (`focusLane`, `asideLane`). `controller.interact()` routes E through `focusLane` as well.
  - Never show two lane surfaces by juggling z-indexes. Give a new surface a rank in `lanes.ts` and a unit test.
  - A new target kind gets a tier in `TIER_U` (`systems/interactables.ts`).
- **Copy:**
  - sentence case;
  - labels start with a verb and are 3 words or fewer;
  - a prompt is a verb plus an object;
  - an error says what happened and how to fix it;
  - use the glossary (planet, classic site, backpack, chest, crafting table, the plaza);
  - no "click here", "OK" or "Submit".
- **Accessibility:**
  - touch targets are at least 44 px;
  - functional text is at least `--text-sm`;
  - sizes are in `rem`, so the "Larger text" setting (`html.text-lg`) scales them;
  - every cue has a text twin (a prompt, a label or a live-region announcement).
- **Touch** (docs: `documentation/game-ui/touch.md`, design system §10): the floating stick, the second-finger view drag and the input modality live in the touch chunk (`input/touch.ts`, with the pure `stick.ts`, `gestures.ts`, `touchCopy.ts`, unit-tested), imported in `game-mount.tsx` only when `(any-pointer: coarse)` matches. It imports nothing from the main bundle but types. Mouse and pen behaviour must stay exactly as it is.
  - Style touch-only changes with `[data-input='touch']` (the last input used), never a pointer media query. Touch copy never names a key; reword announcements in `forTouch`.
  - Every drag and two-finger gesture keeps a single-pointer alternative (tap to walk, the compass buttons). Test touch with real CDP touch events (`Input.dispatchTouchEvent`; a point missing from the next event has lifted, `touchEnd` lifts them all), as the E2E "touch" group does.

### Content (data, not code)

The site's content, IA and navigation are data (spec: [documentation/content/spec.md](./documentation/content/spec.md); plan and Definition of Done: [plan.md](./documentation/content/plan.md)). Until the platform's phase 0 lands, today's pages still hold some copy; don't add more.
- Editorial copy, menu items, content URLs and media paths never go in `src/pages/`, `src/layouts/` or `src/site/`. They go in `content/` (the mock API, shaped exactly like the `/v1` responses) and reach pages only through the repository (`src/site/content/repository.ts`). Interface strings stay in code.
- Content media lives in `content/media/<owner>/<id>/` as a master plus a JSON sidecar (alt, credit, licence, focus), and optionally its dark mode version, `<name>.dark.webp`, named in the sidecar's `dark` and part of the same picture (crops, Replace, Delete and Publish carry it; docs: `documentation/content/media.md` §10). A file to download (the résumé's PDF) is a `document` sidecar beside its PDF, published at `<base>/media/<id>.pdf` by `integrations/content-files.mjs` and linked as `ref:media/<id>` (media §11). A video file is a `video` sidecar beside its MP4 or WebM (kept as uploaded) and its poster frame `<name>.poster.webp`, published at `<base>/media/<id>.<ext>` by the same integration (with byte ranges in dev) and shown by a video block's `media` (media §12). A video must stay under 100 MB (`MAX_VIDEO_BYTES` in `src/site/editor/model/upload.ts`: GitHub refuses bigger files in a push); never add Git LFS (Pages doesn't serve it). Generated sizes are never committed; code-owned assets (the planet's, the design library's samples) stay in `public/`.
- **An article** is `content/articles/<id>.json` (blocks), its masters and sidecars in `content/media/articles/<id>/`, and a node in `content/structures/site.json`. The contract is `src/site/content/schema.ts`; `tests/unit/content.test.ts` checks the files, their references and the media budgets, and `src/pages/[...path].astro` renders every node the structure places (docs: `documentation/content/plan.md` §8).
- **Article illustrations** use the owner's named styles in `assets-src/illustrations/styles/` (the one so far: **ink sketch**, the `ink-sketch` skill in `.github/skills/`): a manifest per article (`assets-src/illustrations/<article>/illustrations.json`, its own theme and cast) driven by `python scripts/illustrate.py` (`gen`, `ink`, `preview`, `publish`, `place`). Light and a redrawn dark version, published as transparent ink-only WebP pairs; propose the set to the owner before generating, and never commit the gitignored style references.
- **Pictures' shapes** are single-sourced in `src/site/design/pictures.ts` (`PICTURE_SPECS`: the lead picture 21:9, filled by default and cropped around its focus point; the thumbnail 3:2, shown whole by default). Every picture use can choose how it's shown (`display`: fill, fit, actual, tile), a colour behind it taken from the picture's own edges (`background`), square corners (`rounded: false`) and a drop shadow that follows its shape (`shadow`, the `c.image.shadow-*` tokens); the defaults are the look above (media §9.1). Draw them through the `Image` fundamental's `display`, `bg`, `rounded` and `shadow` (or, where a wrapper clips the picture, the same filter on the wrapper), never a component's own `object-fit`, radius or shadow; the colour comes from `picture()` (`bg`, the pure `edgeColour.ts`) as data, never a colour in CSS. A page's cards use its `thumbnail`, else its lead picture, with its `thumbnailStyle`. A crop is a copy with a `crop` record in its sidecar, never a change to an original (`cropMedia`; docs: `documentation/content/media.md` §9, `documentation/editor/spec.md` §6.1).
- IDs never change. Slugs and sections can: a moved or renamed page, published or not, just gets its new address, and the old one goes, with no redirect (the owner's call, sections spec D11). Content items never name a channel: the site and the planet each map them through their own structure (`structures/site`, `structures/planet`). Every published item has one canonical page on the site, and everything the planet shows has one (V12, V13).
- **Sections and pages** (spec: [documentation/sections/spec.md](./documentation/sections/spec.md); plan: [plan.md](./documentation/sections/plan.md)). The site is exactly three levels: the home hub, its sections, their pages (V22); every node ID is unique and a moved page keeps its node (V21).
  - A section has a `view` (`list`, `tiles`, `bento`), rendered by `IndexLayout`. A page is the article resource with a `kind` (`note` shown as Article, `page`, `gallery`), which decides its opening.
  - The header's navigation is `menus.primary` in the site structure (sections, pages, custom links), rendered on every page through `siteNav` (`src/site/content/navigation.ts`). Never hardcode a menu.
  - `content/redirects.json` holds only the classic site's old addresses; `[...path].astro` builds a static redirect page for each (V19), and one that no longer fits is skipped with a warning. Never make a move write a redirect or refuse because a page is published. Every structure operation keeps the fields it doesn't touch (`menus`).
- **Recommendations** (spec: [documentation/sections/recommendations.md](./documentation/sections/recommendations.md)): one list, `content/recommendations.json`, shown by a section whose `recommendations` settings say where (start, end, after a page) and how (tiles, rows, wall, spotlight); edited on edit mode's Recommendations screen. The rules are pure in `src/site/content/recommendations.ts`. A person's photo is uploaded, or taken once from a public LinkedIn profile on save and kept as the site's own picture (never linked: LinkedIn's addresses expire); tests never reach LinkedIn (`SITE_EDITOR_PROFILE_PHOTOS=off` on the fixture server, a stand-in fetch in unit tests). Tiles keep their parts level through `subgrid` (checked by the editor E2E); never invent a recommendation in the real content.
- **Gallery (albums)** (spec, plan and Definition of Done: [documentation/gallery/](./documentation/gallery/spec.md)): an album is its own resource, not a page (redesigned 23 October 2026; phases A1 to A6 built, waiting on the owner's review of the whole experience): `content/albums/<id>.json` (a private one in `private-pages/albums/`), placed by a structure node `{type: "album", id}`, with its items (library items and text cards), its order, its cover and its settings, checked by V38 to V55. A picture's words (caption, description, alt text, date taken, place) live on its sidecar, never on the album. Edit mode has an Albums screen and an album editor modelled on Google Photos and Apple Photos, never the article editor; an article of kind `gallery` is refused (V43), and `content.test.ts` fails on the first build's leftovers. The rules are pure in `src/site/content/album.ts`; never work out an order, a count or a default arrangement in a component.
  - A section with the view `albums` draws each album as an `AlbumBand` (bands from `src/site/content/bands.ts`, in the section's `albumOrder`); an album's page is `AlbumLayout` with `AlbumGrid` (`albumPage.ts`); the `album` block shows an album, by its ID, as its band (`content/albumBlock.ts`, the chooser `editor/model/albumBlock.ts`).
  - Edit mode: the Albums screen (`/_edit/albums/`) and the album editor (`/_edit/albums/<id>/`) on the kit's `PhotoGrid`, the viewer and `MediaInfo` (words saved to the sidecar), Edit cover (`model/cover.ts`), and Media as the library (`MediaLibrary`, `model/library.ts`). ### Edit mode (the local CMS)

Spec, plan and Definition of Done: [documentation/editor/](./documentation/editor/spec.md). Edit mode edits `content/` from the browser, on `npm run dev` only (`/_edit/`, or the Edit this page button on any page), and publishes by committing `content/` and pushing.
- **Dev only, by construction:** `integrations/editor.mjs` injects its routes, middleware and launcher for `dev` alone. Nothing of it may reach a build: `verify:prod` fails on `/_edit`, `editor-block`, `--c-editor` or `data-editor` in `dist/` (the docs aside). `CONTENT_ROOT` (another content folder) is for dev and its tests only; a build refuses it.
- **No request value in a script:** a dev-only page or middleware never writes a request value into an inline script; it goes into escaped markup the script reads. A raw middleware page under `/_edit/` runs edit mode's guard (`startingGuard` in `src/site/editor/model/starting.ts`: loopback, Host, never cross-site, never framed) and sends `frame-ancestors 'none'` (`tests/unit/editorStarting.test.ts` feeds it hostile values).
- **One broken file never stops every page** (content spec §5): dev reads with `loadContentLeavingOut`, which leaves out an article or a piece of media that fails the check (and what only it breaks), and edit mode lists them above every screen; the site's own settings, structure, people, overlay and grants still stop it. A build always uses the strict `loadContent`. Never catch a `ContentError` to show a page anyway.
- **Content is read from disk, never imported** (`source.ts`), so a save reloads no module. Writes go only through the store (`src/site/editor/server/store.ts`): versions (409 on a conflict), the content check before any byte is written (422), temp files and ordered renames, rollback. Never write `content/` from editor code any other way.
- **In Atiya Studio the app's title bar draws the top bar** (desktop plan stage 7B): asked with `X-Atiya-Studio`, `EditorLayout` hides its header (`data-studio`) and `scripts/studio.ts` describes it to the app and runs its commands. Put a screen's controls in the header's slots (`title`, `tools`) as usual: they appear in the app's row by themselves. Keep them buttons, links, tags and Selects (what the description knows), named, and with an icon from the icon set.
- **Saved, and live** (editor spec §2.1): every save reports through `saveStatus` (`scripts/client.ts`: `dirty`, `saving`, `saved`, `failed`, `carry` before a screen reloads itself), never a bare "Saving…" text; `announce` is only for a moment's note. Every change is pushed to every open page with its tab (`X-Editor-Tab`, `asTab`) and the content generation; a screen hears changes made elsewhere through `onContentChange` and must keep unsaved input (`scripts/live.ts`), and the article editor takes in its own article's changes or shows the conflict.
- **A screen that manages a collection is list and details** ([documentation/editor/list-and-details.md](./documentation/editor/list-and-details.md)): anything that adds, chooses, edits, orders or removes several things of one kind (Sections, Recommendations, Access, Albums, Home highlights, and every new one) is `SplitView` with `ListPane scroll="rows"` (the screen's settings row in `head`, Add in `add`, the items as `ListLink` rows with an `icon` or a face) beside a `DetailPane` (the chosen item's heading, its Move up and Move down, its form, Save and a two-press Remove). The choice is in the address (`?<key>=`, with `new` and `settings`), choosing swaps one region, and each action saves on its own with the version. Never a single long form or cards with a form each, and never a copy of the layout's CSS: a missing piece is added to the kit with its story. Design it this way from the start, without being asked; only a screen that edits one object or works on a canvas or grid is an exception (named in the spec). `editorDesignSystem.test.ts` holds every `*Manager` part to it.
- **The editor tier:** parts (`src/site/editor/components/`) are made of the kit (`src/site/editor/kit/`), fundamentals, compounds, tier 0 and the editor model only, never another part; `EditorLayout` and the pages (`src/site/editor/pages/`, no styles) compose them. A piece several parts need goes in the kit, or in the website's compounds if the site could use it (SplitView, ActionBar); a recipe for a part's own element goes in `editor-recipes.css`, keyed by a data attribute; scripts find pieces by data attributes. Pure logic goes in `src/site/editor/model/` with unit tests. A screen re-renders what a change affects with `swapRegions` (`scripts/client.ts`); give a region `data-region`. Held by `tests/unit/editorDesignSystem.test.ts`:
  - **controls only through fundamentals:** a part, kit piece or `EditorLayout` never writes `<button>`, `<input>`, `<select>`, `<textarea>` or `<dialog>` (RowButton, TileButton, MenuItem, RadioCard, ColorField, HiddenField and the rest); a new kind of control is a new fundamental with its story; an exception goes in the test's `ALLOWED` with its reason;
  - **parts stay short:** markup and script at most 350 lines, the whole file 650; split a big part into parts the page composes through slots, and move logic to `model/`;
  - **owned tokens:** `c.editor` is shared; a value one part alone reads is its own `c.editor-<name>` group owned by that part; every name starts with `--c-editor` and goes only to `editor-tokens.css`; a script owns nothing (pass it a value through a local custom property);
  - **documented like components:** a comment on every prop and a story in `src/site/editor/stories/` with made-up data from `samples.ts`, shown on the dev-only parts library (`/_edit/library/`);
  - **a part's scope reaches a child's root:** a component that spreads `...rest` on its root takes its parent part's scope, so give kit roots distinctive class names, and wrap a component given `slot="…"` in `<Fragment slot="…">`.
- **A page's place is its section:** `saveArticle` saves it with its section (`structures/site.json`), and a building on the planet shows a section (D12), so a page's building follows and nothing writes Little planet's structure (`structures/modes/little-planet.json`) but the Planet screen's Settings and Ways to explore's starting map (a building's words and the section it shows). Never add a page list back to the planet. Structure operations (`model/structure.ts`, `model/planet.ts`) keep every field they don't change. Sections and Planet are one pattern (`components/SectionManager.astro`, `scripts/manager.ts`: the list of sections beside the chosen one's Pages and Settings tabs): Sections turns `manager:move` and `manager:reorder` into its structure operations (`placeAll`); the Planet screen lists each building's section pages read-only; a change to one screen's manager is a change to both. A new screen's route goes in `integrations/editor.mjs`: a dev server started before needs a restart to serve it.
- **Pictures from their bytes:** read a master with `sharp(readFileSync(path))`, never `sharp(path)`: sharp keeps files it opened by path open, and Windows then refuses to replace or delete them.
- **The action center** (Ctrl+/ in Atiya Studio; [documentation/desktop/action-center.md](./documentation/desktop/action-center.md)) finds what edit mode holds through `GET /_edit/api/find` (`server/find.ts`, from the content index alone: never draw every picture on its path). Edit mode's screens are one list, `SCREENS` in `model/find.ts`, which the side navigation reads too: a new screen goes there, with the other words it's found by. A site setting a card can change goes in `findSettings` and `setFindSetting`, written through the store as its screen writes it (the ways through `server/ways.ts`, never a copy). In the app, finding and ordering are `src/ui/find-rank.mjs`, what's found is `src/ui/find-catalogue.mjs`, and the main process builds every address (`src/core/finder.mjs`): the panel names a result, never a URL. A test presses Ctrl+/ with `sendInputEvent` (Playwright's key presses skip `before-input-event`).
- **Tests never touch the real content or remote:** the E2E group is its own Playwright project, `npx playwright test --project=editor`, on `scripts/editor-test-server.mjs` (port 4330: a git copy of `content/` in `.editor-test/` with a bare remote, and a fixture `private-pages/` submodule with its own bare remote, both reset between tests). To try the editor by hand without touching `content/`, run that script and open `http://localhost:4330/_edit/`.
- **Performance is measured, and waits are honest** (docs: `documentation/engineering/performance.md`, `perceived-performance.md`, the plan in `performance-report.md`): `npm run perf:bench` measures edit mode on the fixture (port 4330) and the production site (port 4332), and `--compare perf/baseline.json --check` catches regressions. In dev, every request is timed with named spans: wrap new costly server work (a content read, a picture, a git process, a check) in `timed` / `timedAsync` (`src/site/content/timing.ts`), and name a new client wait with `performance.measure('editor:<name>')` plus a benchmark step and a target in `perf/budgets.json`. A new wait uses the feedback pattern for its class (instant, responsive, waiting, long): never block or lose input, keep the old view until the new one is ready, and say what's happening in the status line.
- **Never a silent wait, and changes at once** (editor spec §2.2, §3.6): every wait goes through the task tracker (`startTask` / `track` in `scripts/client.ts`, its timings the `c.editor` `feedback-*` tokens): name the element it affects, which shows its sign through `data-busy` (`ack`, `on` past 300 ms, `done`), styled by its own component. A swap names its regions (`swapRegions` sends `X-Editor-Regions`, `model/regions.ts`): a screen draws only what's asked (`wants`) and must never put git, the picker's cards or every picture on a whole screen's path (git is cached in `server/git.ts`: `changes()`, `peekChanges()`, `{ fresh: true }` only before a commit). The picker is drawn on demand (`MediaGrid` `pending` / `paging`, `scripts/picker.ts`). In the article editor, a change of order or presence goes through `change(…, { atOnce: true })` (shown at once by `model/optimistic.ts`, the outline's row template, the forms renamed, the canvas's `remap`), and the canvas is redrawn behind the old one (`reloadCanvas`), never reloaded in view. The dev server's first-start warm-up and starting page are `integrations/editor.mjs`'s (`SITE_EDITOR_WARM=off` turns them off; the E2E fixture server does). E2E: "editor: optimistic edits" and "editor: no silent wait" (`tests/e2e/editor-perf.spec.ts`).

### Protected content (private pages, telemetry)

Spec, plan, Definition of Done and quality benchmark: [documentation/access/](./documentation/access/spec.md). There's one kind of access-controlled page, the **private page** (never call it "locked"): it sits in an open section at an opaque address (`/<section>/<token>/`), listed and opened only for a visitor whose access covers it, sealed (AES-256-GCM) after the build and decrypted in the browser. An access code (typed on the Sign in page) and a magic link are two ways to share any private page, not kinds of page: a grant opens whatever its scope names, either way (V26).
- **Plaintext never goes public.** Private content, its media and the grants live only in `private-pages/`, a git submodule of the private repository `atiya-private` (`scripts/setup-private-pages.ps1` sets up a clone). Never copy a file from it into `content/`, `public/`, `src/`, a test, a doc, a log or a commit message of the public repository, and never print a protected title, ID, slug or token from a script (the sealer and the leak check say counts and folders only).
- **Two origins, one content.** `source.ts` reads `/content/…` and `/private/…` (`PRIVATE_ROOT` in dev and its tests only; a `--mode test` build reads `tests/fixtures/private-pages/`, made-up content whose codes the tests know). Private pages get opaque addresses in their sections, list open pages only (V32), are never on the planet (V28) and never in a menu, a redirect or `contactPage`/`privacyPage` (V25). The loader holds V23 to V32.
- **Sealing:** layouts mark protected regions with comment markers (`<!--sealed:main:<id>-->`, `<!--sealed:card:<id>:<after>-->`); `integrations/seal.mjs` (the last integration) turns them into templates, moves media under `_sealed/<build>/` and writes keyrings under `_access/<build>/`; `scripts/verify-sealed.mjs` fails the build on any leak (words the public sources already hold aren't one: it counts them, by category), and runs in `verify:prod`, the E2E web server and the deploy before upload. Don't weaken it to pass: fix the leak.
- **The runtime** (`src/site/scripts/sealed.ts`) loads only where needed (`scripts/access.ts`), stays ≤ 12 KB gzip, and tells telemetry what happened through `site:access` events, never a code, a secret or a title. Scripts inside a sealed region are re-created after decrypting (`activateScripts`).
- **Agreeing before seeing** (spec §7.6, D23): nothing a grant opens is decrypted until its reader agrees (`UnlockPanel`'s `agree` state, `agreeFirst` in `sealed.ts`). Who and why come from the keyring's `reader` (the recipient's name and organisation, the grant's purpose); a grant's notes, email and role are never shown. The words live in `src/site/access/agreement.ts` and in `UnlockPanel` (a test holds them equal); changing them needs a new `AGREEMENT_VERSION`. Each agreement is kept and emailed by the contact service (`POST /api/access/agreement`, contact spec §4.5). The protected E2E tests start pre-agreed, except the "protected content: agreement" group.
- **Crypto is `src/site/access/`,** pure, for Node and the browser, held to published test vectors (`tests/unit/access.test.ts`). Never hand-roll a primitive or lower the PBKDF2 count; codes are generated, never chosen.
- **Edit mode** writes both folders through the store (`/private/` keys; grant transitions enforced) and saves both with the one **Save to remote** (the button and screen were called Publish until 6 October 2026; **Publish** now means a page's Status becomes Published, set on the page itself: a save to remote never publishes): private first; your message on the public commit only when nothing private changed (`publicMessage`); a refused private push holds the public commit back. A page's access is chosen in the New article dialog and changed in its own settings (`setPageAccess`: the file and its own media move folders in one transaction); a copy keeps its access. Private pages have no screen of their own: they and their media are listed where every page and picture is (Pages, Sections, Media), tagged Private and filterable, and a Sections move that involves one goes through `moveSectionPages` (structure and overlay in one transaction). **Sharing is the Access screen's** (`/_edit/access/`, spec §8.1, D22: `AccessManager.astro`, `GrantDetails.astro`, `scripts/grants.ts`; its words and groups pure in `model/access.ts`): every code and link by state beside the chosen one's details, one save for who, why, notes, what it opens and its last day (`updateGrant`), Withdraw now (keeps the record) and Delete (`deleteGrant`; the store allows it). A private page's Share dialog (`SharingPanel.astro`) shares that page and links each grant to the Access screen; Settings holds no sharing. The media server reads and writes each file where it lives (`private-pages/media/` for a private page's).
- **Telemetry** (PostHog, `posthog-js` pinned, its no-external build): `scripts/telemetry.ts` runs on every page and stays ≤ 1.2 KB gzip (`size-report`); PostHog and the sanitizer (`telemetrySanitize.ts`) are their own chunk, fetched on idle. On protected pages, the Sign in page and any page showing shared cards, only the allowlist leaves the browser; fragments are stripped everywhere. Its key and host are content (`services.telemetry` in `content/site.json`, read by `integrations/services.mjs`), used only in a build for the address `services.telemetry.site` names (against `SITE_URL` and `BASE_PATH`, which both workflows set): never in dev, a local production build, a copy of the site at another address or a test build, and respects GPC, DNT and `?telemetry=off`. A new event goes in the allowlist (both `telemetrySanitize.ts` and the E2E's) only if it carries nothing protected. E2E tests turn it on with `localStorage['site.test.telemetry'] = '1'` and read every request to `https://telemetry.test`.
- **Content Security Policy** (access spec §6.4): every built page carries `<meta http-equiv="Content-Security-Policy">` and a referrer policy first in its head (never in dev), made by `src/site/services/csp.ts` from the site's services; inline scripts are allowed by the hashes `integrations/csp.mjs` collects after the build. Never add an inline event handler, `eval` or a third-party host by hand: a service's hosts go in its catalogue option's `csp`. Checked by `verify-sealed.mjs` and `tests/e2e/csp.spec.ts`.
- **A remembered session ends after 30 days** (`REMEMBER_DAYS`, `deviceSession` in `src/site/access/session.ts`): read a stored session only through `deviceSession` (PageShell's head script mirrors its date rule), never `JSON.parse` the item yourself. **Telemetry never sends a private page's token:** `maskTokens` (`telemetrySanitize.ts`) replaces it with `private` in every string of every event.
- **Security rules beyond a component** (the review: [security-review.md](./documentation/engineering/security-review.md)): workflows trust GitHub's published SSH host key, never `ssh-keyscan`, and never put `${{ github.event.* }}` in a `run:` (`tests/unit/security.test.ts`); the contact service reads a client's IP as the last public `X-Forwarded-For` entry, never the first; keep `npm audit` at 0 for the site, Atiya Studio and the contact service.
- **Check with** the E2E groups "protected content" (the scope matrix, telemetry, sign-out, axe), `--project=editor` (`editor-access.spec.ts`) and `npm run verify:prod`; `npm run preview:protected` builds the real private content sealed, on `http://localhost:4331/`, for your eyes only.

Each kind is **one** instanced draw of 256-item batches, built in the vertex shader from packed data textures (`world/grass/draw.ts`); never instance one mesh per blade (measured about 7× the cost) or add more alpha-card grass (the tufts are the one exception: few, and only in the knee-high meadows).

A new feature that people stand at or walk to gets a worn disc or a trodden segment there.

What it needs (wind, lamplight, pads, noise, the tuft atlas) comes in `world/grassEnv.ts`. Its sway replicates `addSway`'s formula from the same `windUniforms` and `WIND_GLSL`; feet, Chopper, the family and resting drops flatten it (`MOVERS`), so nothing hides in it.
    - Check it with `__game.grass()` (counts, build ms) and `__game.visitMeadow(i)` (stands in a knee-high meadow). E2E tests run it at a quarter density (`openPlanet` sets `localStorage['game.test.grassDensity']`, honoured only outside production); a test about the grass itself passes `{ grass: 'full' }`.
  - **Clouds** are painted sprites (`cloud-atlas` + `cloud-normal`, `world/Sky.tsx`), one alpha-blended instanced draw sorted far to near; the 3D `cloud()` puffs are only the fallback. **Normal maps** go where they add relief the albedo lacks (the clouds' volume, the lawn). Don't put them on painted leaf/conifer cards: the sprite already carries its relief, and a per-leaf normal fights the canopy's volume shading (tried; the crowns read flatter).
  - **Shaders must never output NaN or Inf.** One bad pixel in the HDR buffer is smeared by the bloom's blur over the whole screen, which turns black. Clamp the base of every GLSL `pow()` (`pow(clamp(x, 0.0, 1.0), k)`), and normalize with `v * inversesqrt(max(dot(v, v), 1e-12))`. A value can't be trusted to stay in 0…1 just because it was clamped in the vertex shader: with MSAA a varying is extrapolated past its triangle at edge pixels. `tests/unit/shaders.test.ts` checks every `pow()`. SwiftShader doesn't reproduce this, so check on a real GPU with `npm run perf:audit` (it fails on any NaN pixel) or `__game.hdrScan(1280, 4)`.
  - **Exposure:** the post chain is linear HDR, tone-mapped once by the final `ToneMapping` effect. An effect that outputs a whole image (tilt-shift, any blur or colour effect) must use `BlendFunction.NORMAL`; some `@react-three/postprocessing` wrappers default to ADD, which doubles the radiance and clips highlights. Only additive-by-nature effects (bloom) may ADD. Change brightness through `sceneExposure` (`world/timeOfDay.ts`), never with a per-effect boost.

### Working modes and throughput

Work is measured by **validated progress per hour**, not completeness per task (learned from the owner's focus-notes loop). The owner's time and attention are the constraint: never make him wait on checks a change doesn't need, and never make him micromanage basic quality. This is the repository's setting of agent-orchestration (**Agent kits**): attended is its "work with me", unattended its "keep going unattended".

- **Which mode:** attended while the owner has written in the last 30 minutes; unattended when he says he's away or hasn't written for 30 minutes.
- **Attended** (he's testing and giving feedback): one fix at a time, about **15 minutes from report to a fix he can see**. Run only the fast checks for what changed (**5 minutes or less**): the unit tests it touches, and the one E2E file or group that covers it. Then merge to `main`, push, and say what to reopen (under an owner's hold: stop at validated and ready, unpushed). Never run a full suite, the editor project or `perf:bench` here. Queue new feedback rather than widening the running fix.
- **Unattended** (he's away): deeper work on the plan's critical path in **45-minute time-boxes**, each ending in a merge of what works. Run the full suites (tier 3) before merging. Leave a handoff summary: what's done with evidence, what's in progress, what's waiting on him, and what to try first.
- **Atiya Studio's preview installer** (plan stage 9P): `node scripts/pack-engine.mjs --out <dir>`, `node apps/desktop/scripts/bundle-engine.mjs --engine <dir>/engine-<version>.tgz`, then `npm run dist` in `apps/desktop` (about 6 minutes; `scripts/check-dist.mjs` checks it before and after), and `install.spec.mjs` installs it into a temporary folder, makes a site on the fake GitHub and uninstalls (about 2 minutes; skipped without an installer). The engine goes in as one archive the app unpacks on first start: never ship it as loose files (the installer took over ten minutes). On GitHub, the "Studio preview installer" workflow builds it (by hand: an artifact; a `studio-v*` tag: a draft pre-release). Never tag or publish a release without the owner.
- **Atiya Studio's checks, by what changed:**
  - `apps/desktop/src/ui/*.css`: `test/css.test.mjs`, plus the one `e2e/stage7*.spec.mjs` for that surface.
  - `frame.js` or `frame.html`: that stage's spec.
  - `main.mjs`, `preload.cjs` or `core/`: the unit test for the module, plus the spec of the stage that uses it.
  - The app's whole E2E suite (about 4 minutes) runs only when unattended, or when a change touches the window, the supervisor or setup's flow broadly.
- **Visual changes get their basics right the first time:** before showing the owner, check the component's whole anatomy in light and dark, at rest, hover, active, focus and disabled, with one enlarged capture. Put a test on the anatomy (the segmented control's is `7A.6`), so the same flaw can't come back.
- **Never take his focus:** test and script launches of the app set `ATIYA_BACKGROUND=1` (`e2e/launch.mjs` does). Never restart his running app without asking; say "quit from the tray and reopen" instead.
- **Merge exactly what was tested, and keep branches short:** an hour at most. Fast-forward `main`, push, then run `node scripts/watch-push.mjs`: it waits for **every** run the push started (the deploy, the parity check, anything else) and fails if any did. A push isn't done, and isn't reported done, until it passes. Watching only the deploy once let the parity check fail on five pushes in a row unseen (16 October 2026).
- **Log every step:** one timestamped line in `E:\Projects\Personal\atiya-progress.log` (outside the repository), so the owner can watch.
- **Challenge the approach** every 30 minutes of running work, with the throughput reviewer (`.github/agents/throughput-reviewer.agent.md`, generated from agent-orchestration's), and act on its top finding.

### Validation: run what the change needs, not everything

Headless E2E is slow here (SwiftShader at 1–2.5 fps, one worker, a test build per run: about 1–2 min per test, about 22 min for the full suite). So validation is scoped to the change's blast radius, the way large teams do it: test impact analysis (Microsoft, Google TAP) and predictive test selection (Meta) run the tests a change can affect on every change, keep the full suite for milestones, and fall back to "run everything" when the impact is unclear. Pick the **lowest tier that covers the change**; escalate only for the reasons in tier 3.

| Tier | When | What to run (typical cost) |
|---|---|---|
| **0 – none** | Docs, comments, copy, `README`/spec/AGENTS edits, renames the language server did | Nothing. Proof-read the diff |
| **1 – affected units** | Any code change | `npx vitest related <changed files> --run` (seconds; follows the import graph). Add `npm run check` only if types, props, test-hook signatures or `tests/e2e` types changed. Write or update the unit test for the pure logic you touched |
| **2 – targeted E2E / one look** | A change a unit test can't see: rendering, shaders, input, DOM UI, doors, sound, anything behind `window.__game` | Only the affected test(s): `npx playwright test --reporter=line -g "<test title or describe group>"` (1–2 min each). For visual changes, **one** screenshot of the affected view, not the whole gallery. Re-run just what failed with `--last-failed`. Use `-x` to stop at the first failure |
| **2v – visual** | A change to how the website's components, edit mode's parts or the game's UI look (tokens, styles, markup) | The screenshots of what changed: `npm run visual -- -g "<tier> <Name>"` (a story), `-g "<page>"` or a spec file (`tests/e2e/visual-editor.spec.ts`, `visual-game.spec.ts`); the whole project (about 10 min) after a token or shared-style change. A change that's meant: `npm run visual:update -- -g …`, then look at every listed image before committing |
| **3 – broad** | Only when a trigger below applies | Full `npm test`, `npm run check`, `npm run verify:prod`, full `npm run e2e` |

Tier 3 triggers (these are the "risky change" cases; otherwise don't):
- **Accumulated change:** several features since the last full run (roughly 5+ commits or a day's work), or before a release/deploy or a milestone review. Run it once at that point, not after every change, and in the background (`mode: async`) while other work continues.
- **A behavioural change to shared infrastructure** whose impact the import graph can't bound (adding a field or a test hook doesn't count): `controller.ts`, `Scene.tsx`/post-processing, `GameApp.tsx`, the store, `config.ts`, the test hook's shared helpers, renderer settings, `playwright.config.ts`, `vite`/`astro` config.
- **Dependencies or build:** `package.json`/lockfile changes, new assets, anything that can move the bundle size → `npm run verify:prod` (always for these; it takes about a minute).
- **Gate / production path:** `platform/gate.ts`, `/play` loading, or the test-hook guard → `verify:prod` plus the "capability gate" and "landing & classic" groups.
- A targeted run failed for a reason you don't understand, or the fix touched more than the original change.

Rules of thumb:
- **Start every E2E run through the launcher,** so the owner can watch it in edit mode's Tests screen (`/_edit/tests/`, documentation/editor/test-runs.md): `node scripts/test-run.mjs --by agent --purpose "<why, in a few words>" -- <playwright test arguments>`. It keeps the live reporter on (even with `--reporter=line`), records who started the run, why and on what code, and warns when a test server on 4329 or 4330 would be reused. Answer "is it stuck?" with `node scripts/test-run.mjs status`, not by reading logs. Don't run two E2E runs at once: they slow each other until long tests time out (the screen warns when runs overlap).
- Map the change to E2E groups by area: `visual` (screenshots: its own project, `--project=visual`; run it after any change to how the website, edit mode's parts or the game's UI look), `landing & classic`, `site design system` (the website's components, theme, select, lightbox, carousel, the design library, axe in both modes), `site on a phone` (the website at 320 to 430 px and on its side: reflow, targets, the menu, the tucking header, the font budget), `protected content` (private pages, signing in, sealed media, telemetry), `article minimap` (landmarks, the current one, preview, jumps, touch, a strip in a box), `editor` (edit mode: its own project, `--project=editor`, on the fixture server; `editor: ways to explore` turns the planet off and on, restarts included), `capability gate`, `rendering` (post FX, exposure, textures), `day–night` (sky, lamps, clouds, clock), `view controls`, `landscape & wind` (terrain, water, wading, wind), `doors`, `sound`, `player character`, `planet` (movement, proximity, dialogs, travel, reset, a11y). Run the one or two groups you touched, or a single test by title.
- Don't re-run a check whose inputs haven't changed since it last passed (e.g. unit tests after a docs-only fix, or E2E after only editing a unit test).
- Don't re-capture README screenshots unless the change visibly alters that view.
- A timeout under host load isn't a regression: re-run that one test before investigating, and compare with the baseline only if it fails again.
- Say what you ran and what you deliberately skipped (and why) in the summary, so the next full run knows what's pending.

## Package installation: use Microsoft package feed proxy (required)

This project is developed on a Microsoft-managed device. Direct access to public package registries is blocked or progressively restricted:

- `registry.npmjs.org`
- `pypi.org/simple`
- `files.pythonhosted.org`
- selected NuGet endpoints

All package installs **must** go through the Microsoft package feed proxy. Projects already using approved Microsoft feeds keep working; anything pointing at public registries will fail.

### Feed URLs

| Ecosystem | URL |
|-----------|-----|
| npm | `https://packagefeedproxy.microsoft.io/npm/` |
| PyPI / pip | `https://packagefeedproxy.microsoft.io/pypi/simple/` |

### npm

- Verify: `npm config get registry` → should return `https://packagefeedproxy.microsoft.io/npm/`.
- If `~/.npmrc` (`%USERPROFILE%\.npmrc`) or a project `.npmrc` contains `registry=https://registry.npmjs.org/`, change it to `registry=https://packagefeedproxy.microsoft.io/npm/`.
- Do **not** add a project `.npmrc` (or lockfile `resolved` URLs) pointing at `registry.npmjs.org`.
- This applies to `npm`, `npx`, `pnpm`, `yarn`, `bun`, and MCP servers launched via `npx`.
- The proxy's `latest` dist-tag is sometimes wrong (e.g. `@react-three/fiber` reports a `10.0.0-canary.*` build, `next` reports a canary). **Always pin explicit versions** verified against the package's GitHub releases (`npm install pkg@x.y.z`) instead of relying on `latest`.

### Python

- Use index URL `https://packagefeedproxy.microsoft.io/pypi/simple/` (e.g. in `%APPDATA%\pip\pip.ini` / `pip.conf`, or `--index-url`).
- `uv` does **not** read pip config; configure it explicitly (e.g. `UV_INDEX_URL` / `UV_DEFAULT_INDEX`, or `[[tool.uv.index]]` in `pyproject.toml`).
- Container builds must also use the proxy rather than `files.pythonhosted.org`.

### Common symptoms of misconfiguration

- `npm install` / `npx` fails, MCP servers fail to start, 403 or TLS/connection errors against npmjs.org.
- `pip install` fails reaching `pypi.org`; container builds fail fetching from `files.pythonhosted.org`; `uv pip install` bypasses pip proxy config.

Root cause is usually a personal `.npmrc`, `pip.ini`, or tool-specific config overriding the Microsoft-managed registry. Check those first.
