# Performance report: edit mode and the site, October 2026

A measured audit of edit mode (the local CMS) and the public site: the baseline, where the time goes, what to fix in what order, and how each fix will be proven. Measured with the benchmark in [Measuring performance](performance.md); the feedback rules the plan applies are in [Perceived performance](perceived-performance.md). The planet's game was audited separately ([performance audit](../poc-3d-navigation/performance-audit.md)).

> **TL;DR.**
> - **The site is fast; edit mode isn't.** The production site paints its largest content in under 0.1 s on a desktop and under 0.7 s on a throttled phone, with no layout shift. Every edit mode screen takes 0.9 to 2.5 s to open on a warm dev server, and an edit takes up to 4.2 s to settle.
> - **One cause dominates: git.** Every screen asks git what's waiting to be saved to remote, as 11 git processes run one after another (about 0.9 s on Windows), and the article editor and the dashboard ask twice (26 and 22 processes, 2.1 and 1.8 s). That's 88 to 97% of every screen's time, and it runs again after every save.
> - **The second: whole screens drawn again for small changes.** After typing, the article editor fetches its whole screen again (1.3 MB of HTML, with the 105-picture picker and git twice) to update its outline: 2.4 s. A new block reaches the canvas after 3.2 s, because the canvas reloads too.
> - **The save itself is quick** (0.2 s), and most of that is reading every content file again; so is selecting (20 ms) and opening the picker (50 ms).
> - **The plan, in order:** one cached git status off the critical path (P0, every screen about 0.15 s), region fragments and the picker on demand (P1, an edit settles in about 1 s), the canvas patched in place (P1, a new block in under 0.5 s), then an incremental content snapshot, persistent picture facts and targeted live updates (P2). Feedback fixes go with each step: "Updating…" in the status line, no white canvas, no inspector tab flipping back.
> - **Tracked:** `npm run perf:bench -- --compare perf/baseline.json --check`; every target below is in `perf/budgets.json`.

## 1. Method

| | |
|---|---|
| **Machine** | Intel Core i9-13900K (32 threads), 64 GB, Windows 11 (10.0.26220), Node 24.13, headless Chromium 153 |
| **Content** | The real content (a copy, for edit mode): 15 articles, 124 JSON documents, 117 media files (114.5 MB) |
| **Edit mode** | `astro dev` on the editor's fixture (port 4330), 1600 × 1000; each screen cold (first load after the server starts) and warm (5 loads); 9 interactions, 5 runs each, from the key or click; the dev server's own spans for every step |
| **The site** | The production build on `astro preview`; 6 pages, 5 loads each in an empty cache, on a desktop (1280 × 800) and a phone profile (390 × 844, CPU ×4, 10 Mbps, 40 ms) |
| **Numbers** | Medians of 5 (p75 in the data tables); the raw run is `perf/baseline.json` (commit `5eb7b43`, 13 October 2026) |
| **Caveat** | A fast desktop: a laptop's numbers will be higher, mostly in the same places (git processes, picture decoding and HTML parsing all scale with the CPU) |

## 4. What's already good

- **The save path is sound.** A save is checked and written in 0.2 s, one at a time, with versions and rollback; the status line tells the truth about it.
- **Direct manipulation is instant:** selecting a block (20 ms), opening the picker (50 ms), its pictures (0.27 s).
- **The production site meets every Web Vitals threshold with a wide margin,** on both profiles: LCP 0.06 to 0.09 s on a desktop and 0.28 to 0.66 s on the phone, CLS 0, TBT 0.
- **Feedback foundations exist:** the status line (`saveStatus`, `announce`), the typing guard that holds swaps while someone types, picture shimmer, and the planet's progressive load.

## 7. Risks

- **A cached status that's wrong is worse than a slow one.** The cache keys on the content generation and git's own files (`index`, `HEAD`, the refs), and Save to remote always asks git afresh before it commits.
- **Partial regions can drift from the whole screen.** Each region's partial is the same component the screen draws, and the E2E editor group compares them.
- **Patching the canvas must give the same page.** The block is drawn by the same component as the site's; the existing "the canvas is the public page" E2E test holds it.
- **The benchmark's machine is fast.** Targets are set where a laptop will still feel the difference; R15 measures one.
